# ATSker

ATSker is a private, two-user web application for job hunting with evidence. A user
uploads their résumés and stories once; the application extracts and consolidates them
into a master career database — roles, bullets, skills, education, certifications and
summaries — and a *track* is a named, ordered selection from that database for one kind
of role.

On any given day the user pastes a job posting and receives: two ATS realism scans
(would an ATS read this document correctly, and would a recruiter's boolean search
return this track), a 0–100 Job Match decomposed into four sub-scores, an honest gap
list including disqualifiers, a recommendation of which track to apply with, and
specific edits to make. Every number traces to a rule and every generated sentence to a
stored source: the trajectory *is* the product.

## Architecture

```
Browser ──HTTPS──► Cloud Run (FastAPI + HTMX + Tailwind, scale-to-zero)
                        │
                        ├──► Neon Postgres (users, profiles, tracks, bullets, stories,
                        │                    applications, résumé archives, llm_calls)
                        └──► OpenRouter — chat completions (extraction, grading, generation)
```

Cloud Run: 1 vCPU / 512 MiB, `--min-instances=0`, `--max-instances=2`, region
`us-east4` (co-located with the database). Images are built by GitHub Actions into
Artifact Registry via Workload Identity Federation; there is no local Docker. Secrets
(OpenRouter key, database URL, session secret) live in Secret Manager and are exposed as
environment variables at deploy time. No model weights run anywhere: all generation is
API calls, and every call is cached by content hash.

The database connection is deliberately pool-free (`NullPool`): a kept-alive connection
also keeps a scale-to-zero database awake, which a serverless deployment bills for.

## Module boundaries

```
src/
├── auth/        session, hashing, rate limit
├── parse/       pdfplumber geometry.        may not import extract/
├── extract/     the only module that calls an API
├── normalize/   text → comparable tokens, ES + EN
├── search/      boolean query evaluation.   may not make network calls
├── score/       sub-scores + aggregation.   may not make network calls
├── generate/    suggestions, validators     (pure code, no network)
├── web/         FastAPI routes, HTMX partials, templates
└── i18n/        strings.py, t(key, lang)
```

The three "may not" rules are what keep the deterministic core testable offline: the
normaliser, the parse gate, the boolean evaluator and the scorer can be exercised
against fixtures with no provider and no database, and the model is confined to the two
edges — unstructured text in, structured data out, and structured data in, prose out.
Everything between is ordinary Python.

## Running it locally

```bash
uv sync
cp .env.example .env          # fill DATABASE_URL, OPENROUTER_*, SESSION_SECRET
uv run alembic upgrade head
npm install
npm run build:css             # compiles src/web/static/src.css → app.css
uv run uvicorn src.web.main:app --reload
```

Accounts are created from the CLI, never by public signup:

```bash
uv run python scripts/create_user.py --email you@example.com --name You
```

`src/web/static/app.css` is generated by `npm run build:css` and committed, because the
container serves it without a Node build step; `tests/unit/test_css_classes.py` fails
when a template uses a class the committed build does not contain, which is the reminder
the build step cannot give.

```bash
uv run pytest -q
uv run ruff check src tests scripts
```

## How the score is built

Every analysis produces a **Job Match** 0–100 from four deterministic sub-scores under
weight set `w4`:

- **Skills** (0.40) — the requirements the posting asks for, credited from the evidence
  grading's basis: direct, equivalent (a vocabulary family), transferable, or none.
  Shown as a direct/transfer split.
- **Experience** (0.25) — the years a recruiter would actually count for this posting,
  plus the posting's tasks the candidate has already done.
- **Title** (0.20) — the track's headline and role titles against the posting's title,
  without seniority.
- **Keywords** (0.15) — the posting's own terms, with the vocabulary's aliases.

Two realism checks sit *beside* the number, never inside it:

- **Scan A — document readability.** Deterministic geometry over `pdfplumber` word
  output: invisible text, contact details in the margin, text inside tables,
  multi-column bodies, mojibake, unembedded fonts. Any **blocker caps the score at 40**,
  any **warning at 85**, and the uncapped score is always reported alongside, so the user
  sees what the document would score once the layout is fixed. Word-level findings carry
  their bounding boxes so the interface can render the page and say *where* the problem
  is.
- **Scan B — boolean recall.** One cached call derives the *flat* boolean queries a
  recruiter would run, and a deterministic evaluator answers whether this track appears.
  A query is a gate, not a percentage: recall never changes the Job Match number.

Generated text (a summary and skills block, a bullet rephrased for one posting, bullets a
story supports) is on demand and never during an analysis. Each proposal must pass three
validators before it is shown — provenance (every item cites a stored source), literal
preservation (every number and proper noun exists in that source), skill closure (every
skill named is the user's own, and in a summary is evidenced at level 2 or better) — and
the validators run again server-side on accept, because the proposal travels in a form.

## Evaluation

Scores are compared to labels by **rank order**, not by absolute thresholds. On the dev
split (**n = 12** pairs, `w4`, 2,000 bootstrap resamples):

| Metric | Value | 95% interval |
|---|---|---|
| Kendall τ-b | 0.646 | [0.223, 0.948] |
| Spearman ρ | 0.747 | [0.254, 0.978] |

The labels come from a **blind LLM rater** (`rater_v2`) that deliberately shares the
transfer rubric with the evidence grader. That shared definition is the point — it is
the same construct, defined once — and it is also the caveat: agreement with `rater_v2`
partly reflects that shared rubric and is **not** evidence that recruiters agree. The
independent checks are the operator's own blind labels, any human labels, and, above all,
the `outcome` column as applications accumulate.

**Ablation** (τ-b with each sub-score dropped in turn): Skills 0.657, Experience 0.497,
Title 0.593, Keywords 0.657. Dropping **Experience** (0.497) or **Title** (0.593) lowers
agreement below the full 0.646; dropping **Skills** or **Keywords** (0.657 each) does not
at n = 12. Experience carries the most, and the two that do not move the number at this
sample size are the ones to re-measure once n grows.

The **test split is sealed**: it is scored once, after the scorer is frozen. n ≥ 20 is
pending and no number is published before then.

## Limitations

- **n = 12 on dev.** The intervals are wide (τ-b spans 0.22–0.95); the ranking is more
  trustworthy than any single value.
- **The rater shares the rubric** with the grader, as above. Do not read the agreement as
  recruiter agreement.
- **Title is volatile across languages.** A Spanish title and an English posting can
  describe the same work and still score apart; the sub-score is the one most sensitive
  to the language a track is written in.
- **The test set is small and seen.** n ≥ 20 pending.
- **Boolean recall evaluates the track as a proxy for a profile.** A recruiter's search
  reads a profile, not an uploaded document, so the scan is a proxy by construction.
